## The rule

Lossless. The model is unchanged. Verification is exact.

A request's output is a function of the request and its seed. The cache only changes how fast it comes (DESIGN.md:101, decision 4). Exact by default: the fp16 cache, no pruning (DESIGN.md:103, decision 6). The target's weights stay the one copy a process already has (DESIGN.md:98, decision 1). Greedy, a drafted token is kept only when it equals the token the target's own sample emits at that position, and a mismatch keeps the target's token and stops ([common/sampling.cpp:708](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L708), [common/sampling.cpp:716](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L716), at the same sha; the greedy routine is not part of the pull request's diff). Above temperature 0, the same commit's rejection sampler keeps a draft when its probability p is at least the draft probability q, or a uniform draw is below p/q, and otherwise draws from norm(max(0, p − q)). The comment says that preserves the target distribution ([common/sampling.cpp:741](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L741), [common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)). It does not say the token string matches a run with no drafter.

## Why

One process serves many lanes, and the limit at long context is not the weights. A lane reads its whole cache for every token: 160 MiB of window keys once it is past 1024 tokens, plus 32 KiB per token of context (DESIGN.md:20). The calibrated step is

    step(B) = 58 ms + B × (0.21 ms + lane cache bytes / 210 GB/s)

(DESIGN.md:22). Single-stream decode slows from 9.4 ms to 13.3 ms between a short context and 20K, which is that cache read at about 210 GB/s rather than the bus's 565 (DESIGN.md:20). The measured lane table then falls with context, because each lane reads its own cache for every token; at 42K a lane already costs about 80% of that bandwidth floor (DESIGN.md:90). Lanes pay well at short context and little at long context (DESIGN.md:32).

A step advances a set of spans, each (lane, tokens). A decoding lane brings one token (DESIGN.md:99, decision 2). Verifying k drafted tokens in that step is one span of length 1+k instead of k+1 steps of length 1, so the cache read is paid once for the tokens the step keeps. That is the whole reason to do it. It is not what today's kernels do. Batched attention at 3K context takes about 5 ms for a tile of 32 queries, a lane's single token pays for the whole tile, and the decode path's split-K kernel cannot be used for the span because it gives different bits from the prefill path (DESIGN.md:75). The follow-on that makes the read shared is one attention kernel for every span, splits merged in a fixed order, reading the cache through the block table (DESIGN.md:168). Until a verify span has that property, acceptance does not amortize the read.

The engine's own single-stream note, not a lane measurement: a 4-token verification pass still costs about 1.85× a single step in bytes, free prompt-lookup drafts accept too rarely, and a trained draft model was the thing not done (docs/README.md:168, docs/README.md:170). This design is that trained drafter, on the lane step, with the exactness rule above. The 1.85× is not reused as a speed below.

### What it reads from the target

Not the target's K or V. It reads hidden features at a list of layer visits, `dflash.target_layers` in the GGUF, and the loader requires that list ([src/models/dflash.cpp:52](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dflash.cpp#L52)). The input width is the length of the list times the hidden size ([src/models/dflash.cpp:56](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dflash.cpp#L56)).

On the looped target the index is the visit, not the cache slot. The graph writes `t_layer_inp[visit]` with the tensor entering each visit, through the prelude, each pass of the core, and the tail, and checks that the visit count equals `n_layer` ([src/models/inkling2-loop.cpp:84](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L84), [src/models/inkling2-loop.cpp:121](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L121)). The output path then stores the final RMSNorm, after the residual mix, at `t_layer_inp[n_layer]` ([src/models/inkling2.cpp:426](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2.cpp#L426)). The non-loop graph stores the input of each physical layer the same way ([src/models/inkling2.cpp:457](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2.cpp#L457)). ### How a draft is produced

A token batch is the noise block. With the mask embedding present, slot 0 is the anchor's token embedding, RMSNormed when `tok_norm` is present, and every later slot is a row of `mask_embd` ([src/models/dflash.cpp:441](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dflash.cpp#L441)). ## What inky adds

The target graph stays the graph it is. Four things are new, and none of them is a second way to compute a token.

**Taps, as views.** The features the drafter reads are tensors the step already has: the input of each layer visit, and the final norm after the residual mix. DESIGN's target is the looped model, 24 physical layers of which the middle 12 run 3 times (docs/README.md:80), 48 layer executions (docs/README.md:81). The pull request's visit index is that execution count, and the last tap is the final norm, not a cache slot ([src/models/inkling2-loop.cpp:84](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L84), [src/models/inkling2-loop.cpp:121](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L121)). A tap is a view of the value the kernel wrote. A second computation of the same value would be a second model.

**A decode span of 1+k per lane.** Decision 2's decoding lane brings one token today (DESIGN.md:99). A verify step brings the last committed token again, plus the k drafted tokens. That is the span of length 1+k, and it is the k+1 logit rows the acceptance routine requires ([common/sampling.cpp:745](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L745)). k is `n_max` after the clamp, so for this drafter at most `block_size - 1`. The last committed token is already in the cache. Recomputing it inside the span has to reproduce that row, because a token's numbers depend neither on the span it sits in nor on the other lanes in the step (DESIGN.md:99). The k new tokens are the drafted ones. If every draft is kept, the extra row is one more sample from the target ([common/sampling.cpp:839](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L839)). If one is rejected, the token kept there is the residual draw, not a relabel of the rejected cache row ([common/sampling.cpp:813](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L813)).

The span goes through the same kernels as every other span. The single-stream decode kernel stays unused for a lane. Its fused attention gives different bits, and a cached token computed one way and a cold token computed another way would make the cache change the answer (DESIGN.md:99, DESIGN.md:75). One step stays in flight. The CPU still picks the lanes (DESIGN.md:104, decision 7). The drafter proposes tokens before that step. It is not fused into `encode_decode`, and it is not a second target step.

**The drafter's own cache.** One small cache per drafting lane, holding the context K and V the drafter computed from the taps, in the drafter's layers, not a copy of the lane's window and full blocks. Injection is only for positions that remain committed after the step. The pull request's `accept` does not remove rows ([common/speculative.cpp:1368](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1368)), so inky cannot rely on a later call to undo an injection. `f_rnn` for the next block is the mix at the new last committed token, which means that token has to have been through the target first ([common/speculative.cpp:1497](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1497)). The bonus or the correction is that token when it was not already a committed input. Its features come from the step that consumes it, which is the same one-token work a lane already does.

**Rollback of a rejected suffix.** The lane cache for a position depends only on the tokens up to that position, and a block is sealed only after one lane has finished writing it (DESIGN.md:114). A rejected draft is not sealed, and it does not stay in the unsealed tail. The convolution state exists only at the end of a step. Inside a prefill chunk it is never kept, so a position is a start point only where a step ended (DESIGN.md:74). The recurrent state kept at a start point is the convolution rows, 3.66 MiB (DESIGN.md:116). A verify span can stop at any of its k drafts. The convolution rows at the accepted length have to be the rows a step that ended there would have left, which means the span has to keep them at each position, or recompute from the last position that has them. Dropping the tail without restoring the rows would leave the next token depending on tokens that were rejected.

The correction is not the rejected row with a different id. On a reject the routine draws from the positive part of `p − q` at that row, which was computed from the accepted prefix, and then stops ([common/sampling.cpp:813](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L813), [common/sampling.cpp:836](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L836)). The comment names that draw norm(max(0, p − q)) and says the procedure preserves the target distribution ([common/sampling.cpp:741](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L741)). The K and V written for the rejected drafts, and for any draft after the first reject, are dropped. The correction's own row is written when that token is consumed, not by relabeling the rejected one.

**Acceptance.** Greedy: keep the draft while it equals the target's sample, and on a miss keep the target's token ([common/sampling.cpp:708](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L708), [common/sampling.cpp:716](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L716)). Temperature above 0: the probabilistic draw, q from the packed top 64, rejection against the target's p, the draw seed mixed so it is not the target's ([common/speculative.cpp:1508](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1508), [common/speculative.cpp:1513](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1513)). The routine says this preserves the target distribution ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)). It does not say a fixed seed emits the same tokens as a run with no drafter, because the accept test and the residual draw are extra draws ([common/sampling.cpp:803](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L803), [common/sampling.cpp:821](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L821)). Decision 4 still requires that one request and one seed give one output, and that the cache is not what changes it (DESIGN.md:101). The non-probabilistic temperature path in the pull request is not the one inky uses.

## Batch invariance, and the gates

Batch invariance is DESIGN's heading (DESIGN.md:59). Under it, the same tokens split at different points hash to the same logits (DESIGN.md:61), and a one-token batch was a real bug in that area (DESIGN.md:72). The cold read's word for the same property is batch-invariant (DESIGN.md:71). A verify span is another split. The logits at a kept position match a one-token span of that lane, a span of 1+k, and the same span beside other lanes. `inky spans` and `inky binv` are the checks that already exist for that (DESIGN.md:99, DESIGN.md:61). They have to cover a span that is then truncated.

The layer table's gates are what Rowan called the exactness gates. DESIGN.md does not use those two words. It says "Exact by default", "The cache never changes an answer", and the gate column (DESIGN.md:103, DESIGN.md:101, DESIGN.md:155). Layer 2's gate is bit-identical cache, state, and multi-step logits for a lane alone and in batches, with prime-sized prefill splits, plus agreement with llama.cpp (DESIGN.md:158). For this work the state in that sentence is the convolution rows as well as the cache. The extended gate is the same identity for a verify span that accepts every draft and for one that rejects in the middle, against a run with no drafter, not only against llama.cpp. Layer 4 already requires that temperature 1 with fixed seeds gives the same outputs with and without the cache (DESIGN.md:160). That sentence is about the cache. The drafter does not inherit a token-for-token reading of it. Above temperature 0 the extended gate is the one the rejection routine states: the kept tokens are a draw from the target distribution ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)), and a fixed seed still determines the output (DESIGN.md:101). The token-for-token check is the greedy gate.

CI today checks a short prompt's decode and a long prompt's prefill, and does not check the long prompt's decode position by position, because some of those positions are ill-conditioned in the model itself (DESIGN.md:65). A verify-span gate on a long prompt has to live with that. The comparison that stays well defined is inky against itself, no drafter against drafter, on the tokens it kept. Agreement with llama.cpp stays the short-prompt check it already is.

## What Rowan measured, and the gain that follows from it

These figures are Rowan's, from llama-server built from that pull request, the LM Studio Q4_K_M target, the mainline-format Q8_0 drafter, `draft-n-max` 3, six real agent requests, context between 10K and 50K. They were not re-run for this file.

| | acceptance | tokens per verify step |
|---|---:|---:|
| greedy | 72% | about 3.2 |
| temperature 1 | 59% | about 2.8 |

k = 3. The pair agrees with "one token from the target, plus the fraction of the three drafts that were kept":

    1 + 0.72 × 3 = 3.16, which is the reported about 3.2
    1 + 0.59 × 3 = 2.77, which is the reported about 2.8

That identity is a check that the two reported numbers describe the same thing. It is not a second measurement. Call those yields T. T is 3.2 greedy and 2.8 at temperature 1.

The cache read this would amortize, from DESIGN.md:20, for C at least 1024:

    bytes(C) = 160 MiB + C × 32 KiB
    R(C)     = bytes(C) / 210×10^9 seconds

160 MiB and 32 KiB are the binary units, and 210 GB/s is 210×10^9 bytes/s. The second choice is the one that fits DESIGN's own check: at 20K, R is 3.920 ms, and 9.4 + 3.920 = 13.32 ms, against the stated 13.3 ms (DESIGN.md:20).

| context | cache | R(C), one read | R/T greedy | R/T at temperature 1 |
|---:|---:|---:|---:|---:|
| 10K | 472.5 MiB | 2.359 ms | 0.737 ms | 0.843 ms |
| 20K | 785.0 MiB | 3.920 ms | 1.225 ms | 1.400 ms |
| 42K | 1472.5 MiB | 7.353 ms | 2.298 ms | 2.626 ms |
| 50K | 1722.5 MiB | 8.601 ms | 2.688 ms | 3.072 ms |

If a verify step reads each lane's cache once and returns T tokens, the cache-read time per emitted token is R/T instead of R. The factor is T at every context. It is larger in milliseconds where R is large, which is the 10K to 50K range Rowan measured, and it is a small part of the step where the 58 ms term dominates (DESIGN.md:22, the lane table at DESIGN.md:24). This is not a tok/s claim. The 58 ms is not multiplied by T. Nothing here says the 119 tok/s at 64 lanes and 42K becomes 119 × 3.2 (DESIGN.md:29).

If the span instead reads the cache once per query, a span of 1+k = 4 reads about four times and keeps T tokens. The cache time per emitted token is then 4/3.2 = 1.25× today's at greedy, and 4/2.8 ≈ 1.43× at temperature 1. That is slower on the cache term, not faster. The gain exists only when the span reads the cache once for its queries. DESIGN.md:75 is why that has to be said.

Two costs are not in T. The drafter always runs its full trained block, and Unsloth's block size of 8 means the draft forward behind these numbers was 8 positions wide while 3 were offered ([common/speculative.cpp:1520](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1520), dspark/README.md:3). The target span of 4 tokens also moves more expert bytes than one token. The engine's note puts a 4-token pass at about 1.85× the bytes of one step, for one stream, not for a lane step (docs/README.md:168). Neither number is a wall-clock measurement of these six requests.

What the six requests do not say: wall-clock, the drafter's cost, the extra expert bytes, acceptance at any other k or any other context, and whether six requests are the route. They are acceptance on llama-server, not a speed on inky.

## The smallest first step

One lane. Greedy. k = 3. The Q4_K_M the engine already reads (docs/README.md:75), and the mainline-format Q8_0 drafter named above. The drafter sees the taps of that lane. The step is a span of 1+3 through the same kernels as any other span. A drafted token is kept while it is the argmax. At the first miss the target's token is kept, the suffix of the span is dropped, and the convolution rows at the kept length match a step that ended there. The drafter is injected only up to the kept length.

The gate that says this worked: on a fixed prompt, the kept tokens and the logit hash at each kept position match the same prompt decoded with no drafter, one token at a time. A forced reject, one drafted token replaced before the check, leaves the next token the same as that run. `inky spans` and `inky binv` stay bit-identical on the span that was kept (DESIGN.md:99, DESIGN.md:61). Cache rows and convolution rows after the rollback match the no-drafter lane at the same length (DESIGN.md:74, DESIGN.md:158).

Not in that step: temperature, more than one lane, a measured tok/s, and sealing a speculative tail into the prefix tree. The next gate is temperature 1 with a fixed seed. Two runs with the drafter emit the same tokens, and the acceptance is the rejection test, which preserves the target distribution and does not promise the no-drafter token string ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742), DESIGN.md:101). The lane table is measured after both gates, not before.
