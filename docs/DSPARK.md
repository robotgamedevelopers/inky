## The rule

Lossless. The model is unchanged. Verification is exact.

A request's output is a function of the request and its seed. The cache only changes how fast it comes (DESIGN.md:101, decision 4). Exact by default: the fp16 cache, no pruning (DESIGN.md:103, decision 6). The target's weights stay the one copy a process already has (DESIGN.md:98, decision 1). Greedy, a drafted token is kept only when it equals the token the target's own sample emits at that position, and a mismatch keeps the target's token and stops ([common/sampling.cpp:708](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L708), [common/sampling.cpp:716](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L716), at the same sha; the greedy routine is not part of the pull request's diff). Above temperature 0, the same commit's rejection sampler keeps a draft when its probability p is at least the draft probability q, or a uniform draw is below p/q, and otherwise draws from norm(max(0, p − q)). The comment says that preserves the target distribution ([common/sampling.cpp:741](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L741), [common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)). It does not say the token string matches a run with no drafter.

## Why

One process serves many lanes, and the limit at long context is not the weights. A lane reads its whole cache for every token: 160 MiB of window keys once it is past 1024 tokens, plus 32 KiB per token of context (DESIGN.md:20). The calibrated step is

    step(B) = 58 ms + B × (0.21 ms + lane cache bytes / 210 GB/s)

(DESIGN.md:22). Single-stream decode slows from 9.4 ms to 13.3 ms between a short context and 20K, which is that cache read at about 210 GB/s rather than the bus's 565 (DESIGN.md:20). The measured lane table then falls with context, because each lane reads its own cache for every token; at 42K a lane already costs about 80% of that bandwidth floor (DESIGN.md:90). Lanes pay well at short context and little at long context (DESIGN.md:32).

A step advances a set of spans, each (lane, tokens). A decoding lane brings one token (DESIGN.md:99, decision 2). Verifying k drafted tokens in that step is one span of length 1+k instead of k+1 steps of length 1, so the cache read is paid once for the tokens the step keeps. That is the whole reason to do it. It is not what today's kernels do. Batched attention at 3K context takes about 5 ms for a tile of 32 queries, a lane's single token pays for the whole tile, and the decode path's split-K kernel cannot be used for the span because it gives different bits from the prefill path (DESIGN.md:75). The follow-on that makes the read shared is one attention kernel for every span, splits merged in a fixed order, reading the cache through the block table (DESIGN.md:168). Until a verify span has that property, acceptance does not amortize the read.

The engine's own single-stream note, not a lane measurement: a 4-token verification pass still costs about 1.85× a single step in bytes, free prompt-lookup drafts accept too rarely, and a trained draft model was the thing not done (docs/README.md:168, docs/README.md:170). This design is that trained drafter, on the lane step, with the exactness rule above. The 1.85× is not reused as a speed below.

### What it reads from the target

Not the target's K or V. It reads hidden features at a list of layer visits, `dflash.target_layers` in the GGUF, and the loader requires that list ([src/models/dflash.cpp:52](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dflash.cpp#L52)). The input width is the length of the list times the hidden size ([src/models/dflash.cpp:56](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dflash.cpp#L56)).

On the looped target the index is the visit, not the cache slot. The graph writes `t_layer_inp[visit]` with the tensor entering each visit, through the prelude, each pass of the core, and the tail, and checks that the visit count equals `n_layer` ([src/models/inkling2-loop.cpp:84](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L84), [src/models/inkling2-loop.cpp:121](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L121)). ### How a draft is produced

A token batch is the noise block. ## What inky adds

The target graph stays the graph it is. What is new is the steps at the end. None of it is a second way to compute a token.

**Taps, copied out of the step.** The features the drafter reads are tensors the step already has: the input of each layer visit, and the final norm after the residual mix. DESIGN's target is the looped model, 24 physical layers of which the middle 12 run 3 times (docs/README.md:80), 48 layer executions (docs/README.md:81). The pull request's visit index is that execution count, and the last tap is the final norm, not a cache slot ([src/models/inkling2-loop.cpp:84](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L84), [src/models/inkling2-loop.cpp:121](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/inkling2-loop.cpp#L121)). A second computation of the same value would be a second model. What the code does: those tensors do not outlive the step. Hidden states sit in the batch arena's rotating pool, `B_NVEC = 10` (`src/engine.rs:314-315`), and a vector is handed out again once it is not in the live set (`src/engine.rs:348-360`). A tap is a view only while that vector is still the one just written. Keeping it is a copy into a per-lane buffer during the step, which is part of the drafter-cache step below. The visit ids are still not listed in this file.

**A verify span of 1+k per lane.** Decision 2's decoding lane brings one token today (DESIGN.md:99). A verify step brings the last committed token again, plus the k drafted tokens. That is the span of length 1+k, and it is the k+1 logit rows the acceptance routine requires ([common/sampling.cpp:745](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L745)). k is `n_max` after the clamp, chosen per step, so for this drafter at most `block_size - 1`. The draft forward is still the full trained block when `n_max` is smaller (`common/speculative.cpp:1520`). The verify span is not that block. With Unsloth's block size of 8, `t = 8` is only the case `k = 7`. The measurement's `k = 3` is a verify span of 4. The last committed token is already in the cache. Recomputing it inside the span has to reproduce that row, because a token's numbers depend neither on the span it sits in nor on the other lanes in the step (DESIGN.md:99). The k new tokens are the drafted ones. If every draft is kept, the extra row is one more sample from the target ([common/sampling.cpp:839](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L839)). If one is rejected, the token kept there is the residual draw, not a relabel of the rejected cache row ([common/sampling.cpp:813](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L813)).

What the code does: `encode_spans` returns the last row's logits of each span, not one row per position. The per-row logits step is what makes the k+1 rows true. Until that step, a call to `encode_spans` is not a verify, and lossless is not a property of it.

A span with `t > 1` cannot use `encode_decode`, which asserts every span has `t = 1` (`src/engine.rs:1480`). It goes through the prefill kernels. On the fp16 path that attention is `k_attn_h`, in tiles of 32 queries (`src/engine.rs:1740-1743`). The single-stream decode kernel stays unused for a lane. Its fused attention gives different bits, and a cached token computed one way and a cold token computed another way would make the cache change the answer (DESIGN.md:99, DESIGN.md:75). One step stays in flight. The CPU still picks the lanes (DESIGN.md:104, decision 7). The drafter proposes tokens before that step. It is not fused into `encode_decode`, and it is not a second target step. Serve does not make this call today. Its generate step is `encode_decode` of `t = 1` (`src/serve.rs:222-223`). A verify step is scheduler work, named below.

**The drafter's own cache.** One small cache per drafting lane, holding the context K and V the drafter computed from the taps, in the drafter's layers, not a copy of the lane's window and full blocks. What the code does: a `Lane` is `kv_swa`, `kv_full`, `cs`, `toks`, `tier`, and `prune` (`src/engine.rs:392-402`), and `Engine::load` asserts `inkling2_loop` and loads one weight set (`src/engine.rs:516-517`). There is no drafter state on the lane and no second file. The cache, and where it sits, is new machinery, not a reuse. That is its own step. Injection is only for positions that remain committed after the step. The pull request's `accept` does not remove rows ([common/speculative.cpp:1368](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1368)), so inky cannot rely on a later call to undo an injection. `f_rnn` for the next block is the mix at the new last committed token, which means that token has to have been through the target first ([common/speculative.cpp:1497](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1497)). The bonus or the correction is that token when it was not already a committed input. Its features come from the step that consumes it. Drafting the next block waits on that pass. That is a scheduling constraint, not a second target step running beside this one.

**Rollback of a rejected suffix.** The lane cache for a position depends only on the tokens up to that position, and a block is sealed only after one lane has finished writing it (DESIGN.md:114). That sealing is a later layer. Layer 2 has no block table, so on this code a rejected tail is simply not read again, which holds only with the fences in the rollback step. The convolution state exists only at the end of a step. Inside a prefill chunk it is never kept, so a position is a start point only where a step ended (DESIGN.md:74). The recurrent state kept at a start point is the convolution rows, 3.66 MiB (DESIGN.md:116). A verify span can stop at any of its k drafts. The convolution rows at the accepted length have to be the rows a step that ended there would have left. What the code does: `k_state_upd` overwrites each channel's three rows with the last three inputs of the whole span (`src/prefill.metal:400-411`), and `layer_b` runs it at `t = sp.t`, the untruncated length (`src/engine.rs:1732-1735`, `src/engine.rs:1769-1773`, `src/engine.rs:1866-1870`). There is no per-position state and no recomputation. The step is to keep the convolution state at each position, or recompute it from the last position that has it. Cache rollback of the rejected positions is the same kind of step. Dropping the tail without one of those two would leave the next token depending on tokens that were rejected.

The correction is not the rejected row with a different id. On a reject the routine draws from the positive part of `p − q` at that row, which was computed from the accepted prefix, and then stops ([common/sampling.cpp:813](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L813), [common/sampling.cpp:836](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L836)). The comment names that draw norm(max(0, p − q)) and says the procedure preserves the target distribution ([common/sampling.cpp:741](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L741)). The K and V of the rejected drafts, and of any draft after the first reject, do not stay in the lane. That is the cache half of the rollback step, not a drop the span already performs. The correction's own row is written when that token is consumed, not by relabeling the rejected one.

**Acceptance.** Greedy: keep the draft while it equals the target's sample, and on a miss keep the target's token ([common/sampling.cpp:708](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L708), [common/sampling.cpp:716](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L716)). Temperature above 0: only the probabilistic path. q comes from the packed top 64, rejection runs against the target's p, and the draft seed is mixed so it is not the target's ([common/speculative.cpp:1508](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1508), [common/speculative.cpp:1513](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1513)). The other path in the pull request fills the draft rows with zeros, so the in-graph chain is argmax and does not condition the next slot on a sampled token ([common/speculative.cpp:1534](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1534), [src/models/dspark.cpp:317](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/src/models/dspark.cpp#L317)). Inky does not implement that path. What the code does: there is no rejection sampler. `Sampler::sample` returns a token and discards every candidate's probability (`src/sampler.rs:29-61`). It never sees q. The llama.cpp routine says the probabilistic path preserves the target distribution ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)). That sentence becomes true of inky only after the rejection-sampler step exists. It does not say a fixed seed emits the same tokens as a run with no drafter, because the accept test and the residual draw are extra draws ([common/sampling.cpp:803](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L803), [common/sampling.cpp:821](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L821)). Token identity at temperature above 0 is still not promised. Decision 4 still requires that one request and one seed give one output, and that the cache is not what changes it (DESIGN.md:101). For the preservation claim, p and q are the same truncation, the softcap is one function of the logits for both, and the request seed owns both streams. Those three are part of the sampler step, not properties of `Sampler` today. Serve's target distribution is top-64 then top-p (`src/serve.rs:179`, `src/sampler.rs:31-60`). The softcap runs after that top-k (`src/sampler.rs:30`, `src/sampler.rs:46-52`). The draft head applies softcap to `base + bias` before its top-64 draw (`src/models/dspark.cpp:364`). One order, in the new sampler, or p/q compares two functions.

## Batch invariance, and the gates

Batch invariance is DESIGN's heading (DESIGN.md:59). Under it, the same tokens split at different points hash to the same logits (DESIGN.md:61), and a one-token batch was a real bug in that area (DESIGN.md:72). The cold read's word for the same property is batch-invariant (DESIGN.md:71). A verify span is another split. The logits at a kept position have to match a one-token span of that lane, a span of 1+k, and the same span beside other lanes. What the code does: `inky binv` hashes the final logits across disjoint split points (`src/main.rs:273-307`). `inky spans` compares a lane alone with a batch of disjoint `(p0, t)` items (`src/main.rs:379-431`). Neither recomputes an already-cached position inside a longer span and then keeps a prefix. That overlapping probe is part of the per-row logits step's gate, not a property these two checks already have.

The layer table's gates are what Rowan called the exactness gates. DESIGN.md does not use those two words. It says "Exact by default", "The cache never changes an answer", and the gate column (DESIGN.md:103, DESIGN.md:101, DESIGN.md:155). Layer 2's gate is bit-identical cache, state, and multi-step logits for a lane alone and in batches, with prime-sized prefill splits, plus agreement with llama.cpp (DESIGN.md:158). For this work the state in that sentence is the convolution rows as well as the cache. The extended greedy gate is the same identity for a verify span that accepts every draft and for one that rejects in the middle, against a run with no drafter, not only against llama.cpp. It is not shown until the per-row logits and the rollback steps exist. Layer 4 already requires that temperature 1 with fixed seeds gives the same outputs with and without the cache (DESIGN.md:160). That sentence is about the cache. The drafter does not inherit a token-for-token reading of it. Above temperature 0 the gate the rejection routine states is that the kept tokens are a draw from the target distribution ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742)), and a fixed seed still determines the output (DESIGN.md:101). That distributional gate belongs to the rejection-sampler step. A golden hash of logits does not show it. The token-for-token check is the greedy gate only. Token identity at temperature above 0 is not that gate.

CI today checks a short prompt's decode and a long prompt's prefill, and does not check the long prompt's decode position by position, because some of those positions are ill-conditioned in the model itself (DESIGN.md:65). A verify-span gate on a long prompt has to live with that. The comparison that stays well defined is inky against itself, no drafter against drafter, on the tokens it kept. Agreement with llama.cpp stays the short-prompt check it already is.

If a verify step reads each lane's cache once and returns T tokens, the cache-read time per emitted token is R/T instead of R. The factor is T at every context. It is larger in milliseconds where R is large, which is the 10K to 50K range Rowan measured, and it is a small part of the step where the 58 ms term dominates (DESIGN.md:22, the lane table at DESIGN.md:24). This is not a tok/s claim. The 58 ms is not multiplied by T. Nothing here says the 119 tok/s at 64 lanes and 42K becomes 119 × 3.2 (DESIGN.md:29). The one-read-per-span property is the shared-read kernel (DESIGN.md:168). It is not what `k_attn_h` does, and it is not what the first step buys.

If the span instead reads the cache once per query, the measured case is a span of 1+k = 4, which is `k = 3`, not a span of `t = 8`. That span reads about four times and keeps T tokens. The cache time per emitted token is then 4/3.2 = 1.25× today's at greedy, and 4/2.8 ≈ 1.43× at temperature 1. That is slower on the cache term, not faster. The gain exists only when the span reads the cache once for its queries. DESIGN.md:75 is why that has to be said. The first step is this slower case. It exists to land the gates.

Neither number is a wall-clock measurement of these six requests.

What the six requests do not say: wall-clock, the drafter's cost, the extra expert bytes, acceptance at any other k or any other context, and whether six requests are the route. They are acceptance on llama-server, not a speed on inky.

## The span width

The draft forward and the verify span are different widths. The pull request decodes the full trained block even when `n_max` is smaller, then the host reads the first `n_max` mask slots ([common/speculative.cpp:1520](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1520), [common/speculative.cpp:1573](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1573)). Slot 0 is the anchor, so the host offers at most `block_size - 1` draft tokens ([common/speculative.cpp:1431](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/speculative.cpp#L1431)). Unsloth's block size is 8, a checkpoint note, not a constant in the loader (dspark/README.md:3). On that file the draft forward is 8 positions wide.

The verify span is `1 + k`. `k` is chosen per step, at most 7 on that file. `t = 8` is only the case `k = 7`. Rowan, on 2026-11-23, set the verify span at `t = 8`, the whole block including the anchor. This revision corrects that. Verifying a fixed 8 when the measurement's `k` is 3 would write K/V and convolution rows for positions the host will not keep, and those rows would have to be rolled back. The measured run is a verify span of 4. The yields above stay attached to `k = 3`. They are not retargeted at `k = 7`.

The drafter runs in-process, on the same lanes as the target. It is not a second server. Nothing in the steps is built.

## What the code does, and the steps that make this true

Each step is one finding from the cold read: what the code does, then the change that would make the design true. The order is bottom up. The greedy first run uses steps 1, 2, 4, and 5. Temperature waits on step 3. No step is a claim that `encode_spans` already verifies.

### 1. Per-row logits

What the code does. `encode_spans` computes logits for the last row of each span. The comment says "for its last row" (`src/engine.rs:1471-1472`). The branch takes `last = row0[si] + sp.t - 1` and runs one output projection per span (`src/engine.rs:1555-1571`). A single span's row is `logits()` (`src/engine.rs:735-737`). Span `i` of a multi-span step is `span_logits(i)`, one vocabulary row (`src/engine.rs:484-487`). The batch-arena field is commented as one vocabulary row per span (`src/engine.rs:202-203`) and allocated `t.min(MAX_SPANS)` such rows, where `t` is the batch's token capacity (`src/engine.rs:243`). The argmax flag writes one token, at `toks[p0 + t]`, from that last row (`src/engine.rs:1564-1570`). Greedy and rejection both need one logit row more than there are draft tokens (`common/sampling.cpp:745`). Those rows are not produced.

The step. Per-row logits. Extend the arena so a span stores one vocabulary row per position, and extend that logits branch so it writes every row, not the last. A verify span of `1 + k` then holds the `k + 1` rows. `span_logits` names the row. The single-span path's one row in the decode arena moves with the same change. One call to today's `encode_spans` is not this step.

The gate. On one lane, hash the logits at each row of a span against the same positions run as spans of `t = 1`. The overlapping-span probe is part of this gate: decode to position `p`, run a span that starts at the already-cached position `p - 1` with length `1 + k`, keep a prefix, and hash the cache and the logits against the run that never drafted. Until that probe is green, greedy identity is not shown. The golden-hash gate does not show that a sampled distribution was preserved.

### 2. Rollback at the accepted length

What the code does. `k_state_upd` sets each channel's history to the last three raw inputs of the span it was given (`src/prefill.metal:400-411`). `layer_b` dispatches it once per convolution site per span with `t = sp.t`: K and V (`src/engine.rs:1732-1735`), the attention post-conv (`src/engine.rs:1769-1773`), and the FFN post-conv (`src/engine.rs:1866-1870`). After the span, `cs` is the state at the end. The next token's convolution reads that history (`src/prefill.metal:384-396`). `get_cs` and `set_cs` copy the whole buffer (`src/engine.rs:2470-2473`). Serve snapshots it once, at the end of the prompt (`src/serve.rs:207`), and restores it when a later request extends that prompt (`src/serve.rs:174-176`). `copy_lane_prefix` copies a prefix of K/V and then the whole of `cs` (`src/engine.rs:466-477`). Nothing stores the convolution rows of an earlier position in the span.

Full-attention K/V is addressed by position. Sliding K/V is written back into a ring of `EXT` keys (`src/engine.rs:1731`). If the lane's length does not advance past the accepted prefix, a later span's `p0` does not attend those rows, and a later encode of the same position overwrites them. That is "never referenced again," not an undo. Three fences belong to the step, and none of them is checked today. Nothing seals past the accepted length. On layer 2 there is no block table; a later seal seals at the accepted length, not at the end of the span. `encode_spans` does not stage the disk tier. Staging is on the single-token `step` path (`src/engine.rs:2168-2170`). This work does not run on a `--kv-disk` lane until a later page says how. `cs_at_prompt` is cleared on admission (`src/serve.rs:180`). A snapshot kept so a span can be rolled back uses a different slot, so a rejected tail cannot become the next turn's resume point.

The step. Keep the convolution state at each position of the span, or recompute it from the last position that has it, so the rows at the accepted length match a step that ended there. Cache rollback of the rejected positions is the same kind of step: the length stops at the accepted prefix and the three fences hold, or those positions are recomputed. The correction token is not a relabel of the rejected row. Its K and V are written when that token is consumed (`common/sampling.cpp:813`). The gate hashes the lane with `lane_hash`, which covers `cs` and both K/V buffers (`src/engine.rs:455-460`): one forced reject in the middle of the draft, and one at the last draft position. A match of the logits at the reject position alone does not pass it.

### 3. A rejection sampler

What the code does. There is no rejection sampler. `Sampler::sample` keeps a top-k of the raw logits, applies the softcap and the temperature, cuts top-p, draws once from one `splitmix64` stream, and returns a token (`src/sampler.rs:29-61`, `src/sampler.rs:19-27`). The stream is seeded once per sampler (`src/sampler.rs:13-14`). The probability of the chosen token is discarded, and q is never an argument. Serve builds one sampler per request, `Sampler::new(j.temp, 64, j.top_p, eng.softcap, j.seed)` (`src/serve.rs:179`), and advances it once per emitted token (`src/serve.rs:210`, `src/serve.rs:228`). No accept test of the form p/q exists under `src/`.

The step. A rejection sampler, with tests. It is new code, not a citation of `common/sampling.cpp` as if that file were callable. p and q use the same truncation: the top-64 serve already fixes, then the same top-p. The softcap is one function for both. Inky's sampler applies it after the top-k (`src/sampler.rs:46-52`). The draft head applies `softcap * tanh((base + bias) / softcap)` before the top-64 draw (`src/models/dspark.cpp:364`, `src/models/dspark.cpp:366`). The step picks one order and uses it for p and for q. The request seed owns both streams. The pull request reseeds the draft generator per request, not per round, and mixes that seed with `0x85ebca6b` (`common/speculative.cpp:1470`, `common/speculative.cpp:1513`). The step gives that pair an owner on the request. It does not take the extra draws from the one stream that already emits the tokens, and it does not leave the owner unnamed. The distribution is unchanged only after this sampler exists. Token identity at temperature above 0 is still not promised (`common/sampling.cpp:803`, `common/sampling.cpp:821`). Temperature above 0 uses only the probabilistic path. The argmax chain is not implemented (`common/speculative.cpp:1534`, `src/models/dspark.cpp:317`).

The gate is distributional, not a hash. One fixed prompt, temperature 1, many seeds: the token emitted at the first position after the prompt, drafter on against drafter off. And the same seed with the drafter emits the same string on two runs (DESIGN.md:101). The golden hashes are a determinism check of the bytes already emitted. They are not this gate. The six-request acceptance rates stay motivation, not a gate. The 1.85× byte figure stays quarantined as single-stream (docs/README.md:168).

### 4. The drafter's own cache

What the code does. The lane holds no drafter state. Its fields are the two K/V buffers, `cs`, `toks`, the tier, and prune (`src/engine.rs:392-402`), allocated at `src/engine.rs:436-443`. The engine loads one `inkling2_loop` file (`src/engine.rs:516-517`). Weights are one mapped buffer, addressed by file offset (`src/engine.rs:597`, `qw` at `src/engine.rs:258-262`). There is no draft K/V, no Markov state, no tap buffer, no per-lane draft generator, and no DFlash tensor table. "One small cache per drafting lane" is not a reuse of `kv_swa`, `kv_full`, or `cs`.

The step. The drafter's own cache, and where it sits. New machinery. One cache per drafting lane, the context K and V the drafter computed from the taps, in the drafter's own layers. It sits beside the lane. The drafter's weights are one copy on the engine, not one per lane. The target's embeddings and output stay the one copy the process already has, borrowed where the draft file omits them (`src/models/dflash.cpp:93`). Draft compute is its own dispatches on the scheduler thread, between target steps. Its scratch is accounted apart from `BArena` and from `ensure_dbatch`. This page does not invent a tensor or a width. The step writes the byte count from the file's own fields: how many draft layers, which of them are sliding, heads, head dimension, window, and the context cap the driver gives the draft, which is the target's (`common/speculative.cpp:3252`). A measured total at 64 lanes is reported beside `kv_bytes()` (`src/engine.rs:1900-1902`). A dense draft layer grows with context. "Small" is not a size until that number is written. Unsloth's "3-layer" note is the checkpoint, not this count (dspark/README.md:3).

Taps are filled in this step, because the cache is filled from them. The copy happens while the batch vector is still live, for every position of the verify span, before the CPU has accepted or rejected. After acceptance, positions that were not kept are not injected. The pull request's `accept` does not remove rows (`common/speculative.cpp:1368`). The next block cannot be drafted until the new last token, bonus or correction, has been through the target, because that is where `f_rnn` comes from (`common/speculative.cpp:1497`). The scheduler does not overlap that draft with the target pass it depends on.

The draft-side projections are not entries in `KERNELS` (`src/engine.rs:84-90`). `joint_proj` on the RNN path is a shape the page already records from the pull request (`src/models/dspark.cpp:93`), not a kernel inky has. This step does not treat an existing target kernel as that projection, and this page names no new kernel for it.

### 5. A verify step on the scheduler

What the code does. Serve generates with `encode_decode` and `t = 1` (`src/serve.rs:222-223`). `encode_decode` asserts that (`src/engine.rs:1480`), so it cannot carry a verify span. A span with `t > 1` is the prefill entry `encode_spans` (`src/engine.rs:1473`). That entry is not a verify: it still returns one logit row per span, and serve never calls it for a generating lane. Several spans require `hgemm` (`src/engine.rs:1487`). If the tensor layout check fails, `load` clears `hgemm` (`src/engine.rs:640-645`) and a multi-lane verify cannot run. The session path releases the batch arena when generation starts (`src/session.rs:82`). Serve does not. An earlier citation of `src/engine.rs:2694` for the span slice was the wrong line. The step. The scheduler learns a third kind of step. Lanes that are generating and have a draft are `encode_spans` of length `1 + k`, `k` chosen for that step, not `encode_decode` of `t = 1`, and not `encode_prefill`. One lane can run without `hgemm`. More than one lane cannot. The drafter's dispatches from step 4 run on that same thread, before the verify, and only once the taps they need already exist. The first run is one lane, greedy, the Q4_K_M the engine already reads (docs/README.md:75), and the mainline-format Q8_0 drafter named above. `k` for that run is the measurement's 3 unless a run records another, so the span is 4, not 8. It is expected to be slower per emitted token than today's `t = 1` decode, because the cache read is not shared yet (DESIGN.md:75). The run exists to land the gates. The `R/T` table is the later kernel.

The gate of that run. On a fixed prompt, the kept tokens and the logit hash at each kept position match the same prompt decoded with no drafter, one token at a time. The forced rejects of step 2 leave the next token and `lane_hash` the same as that run. `inky spans` and `inky binv` stay the disjoint checks they are. They are not restated as this probe. Not in that run: temperature, more than one lane, and sealing a speculative tail. Temperature is step 3's gate: two runs with the same seed and the drafter emit the same tokens as each other, the distribution matches the drafter-off run in the sense that step states, and the no-drafter token string is not promised ([common/sampling.cpp:742](https://github.com/ggml-org/llama.cpp/blob/e4b1cb5318f1ac55d148be228c6347c6a94cc4c6/common/sampling.cpp#L742), DESIGN.md:101).
